# Claims Management System Specification

## Business Objective

Build a tool for claim managers to create and review claims with multiple associated damages. The system must keep claim totals consistent, enforce claim lifecycle rules, and provide a reactive frontend experience where totals update immediately when damages change.

The solution follows Spec Driven Development. This specification and `docs/openapi.yaml` are the source of truth for implementation, tests, and documentation.

## Scope

Stage 1 defines the product and API contract only. Backend and frontend implementation are intentionally out of scope for this stage.

The complete solution will include:

- A Node.js and TypeScript backend using NestJS, Dependency Injection, MongoDB, validation, and REST endpoints.
- An Angular frontend using Dependency Injection, reactive forms, and efficient reactive state for total calculation.
- Backend unit tests with coverage greater than 95%.
- Integration tests proving server-side `totalAmount` consistency.
- `AI_LOG.md` documenting AI usage and human supervision.

## Data Model

### Claim

```ts
type ClaimStatus = 'PENDING' | 'IN_REVIEW' | 'FINISHED' | 'CANCELED';

interface Claim {
  id: string;
  title: string;
  description: string;
  status: ClaimStatus;
  totalAmount: number;
  damages: Damage[];
  createdAt: string;
  updatedAt: string;
}
```

Field rules:

- `id` is generated by the backend.
- `title` is required.
- `description` is required.
- `status` is generated and managed by backend state transitions.
- `totalAmount` is calculated by the backend and never accepted from client input.
- `damages` contains the associated damage records for the claim.
- `createdAt` and `updatedAt` are generated by the backend.

### Damage

```ts
type DamageSeverity = 'LOW' | 'MID' | 'HIGH';

interface Damage {
  id: string;
  part: string;
  severity: DamageSeverity;
  imageUrl: string;
  price: number;
  score: number;
}
```

Field rules:

- `id` is generated by the backend.
- `part` is required.
- `severity` is required and must be `LOW`, `MID`, or `HIGH`.
- `imageUrl` is required and represents the damage image reference.
- `price` is required, numeric, and positive.
- `score` is required and must be an integer from 1 to 10.

## Damage Text Field Decision

The challenge contains a naming inconsistency. The data model defines `Damage.part`, while the form validation section mentions `description` as a required damage field.

This implementation uses `part` consistently in the API, frontend, persistence model, and tests. The damage creation form will label or map its required textual field to `part`. This keeps the solution aligned with the explicit data model and avoids maintaining two names for the same concept.

## Claim Lifecycle

A claim starts as `PENDING`.

Allowed statuses:

- `PENDING`: The claim is created and damages can still be managed.
- `IN_REVIEW`: The claim is under review and damages can no longer be managed.
- `FINISHED`: The claim review is complete.
- `CANCELED`: The claim was canceled before review completion.

Terminal statuses:

- `FINISHED`.
- `CANCELED`.

## State Transition Rules

Allowed transitions:

| From | To |
|---|---|
| `PENDING` | `IN_REVIEW` |
| `PENDING` | `CANCELED` |
| `IN_REVIEW` | `FINISHED` |
| `FINISHED` | none |
| `CANCELED` | none |

Rules:

- A claim must pass through `IN_REVIEW` before it can become `FINISHED`.
- Direct `PENDING -> FINISHED` transitions are rejected.
- `FINISHED` and `CANCELED` are terminal states.
- Status transition logic must live in backend business logic, not in controllers or Angular components.
- The implementation must use a State Machine pattern or equivalent domain-level transition policy.

## High-Severity Finish Policy

A claim with at least one damage where `severity` is `HIGH` can move to `FINISHED` only when the claim `description` has more than 100 characters.

Rules:

- This policy is evaluated when transitioning from `IN_REVIEW` to `FINISHED`.
- Claims without high-severity damages do not require the extra description length rule.
- This policy belongs in the backend domain/application layer.
- The frontend may help users understand the rule, but the backend is authoritative.

## Damage Management Rules

Damages can only be created, updated, or deleted when the claim status is `PENDING`.

Rules:

- Adding damage to `IN_REVIEW`, `FINISHED`, or `CANCELED` claims is rejected.
- Updating damage in `IN_REVIEW`, `FINISHED`, or `CANCELED` claims is rejected.
- Deleting damage from `IN_REVIEW`, `FINISHED`, or `CANCELED` claims is rejected.

## totalAmount Calculation Rule

`totalAmount` is a backend-owned derived field.

Formula:

```text
totalAmount = sum(claim.damages[*].price)
```

Rules:

- The backend never accepts `totalAmount` in create or update request bodies.
- The backend returns `totalAmount` in claim responses.
- `totalAmount` is recalculated after adding a damage.
- `totalAmount` is recalculated after updating a damage price.
- `totalAmount` is recalculated after deleting a damage.
- `totalAmount` may be persisted in MongoDB for efficient claim list reads, but it must be treated as derived data.
- Integration tests must verify that server-side `totalAmount` matches the sum of persisted damage prices.

## Validation Rules

### Claim Create

- `title` is required and must be a non-empty string.
- `description` is required and must be a non-empty string.
- `status`, `totalAmount`, `damages`, `createdAt`, and `updatedAt` are not accepted from client input.

### Claim Update

- `title` is optional, but if provided it must be a non-empty string.
- `description` is optional, but if provided it must be a non-empty string.
- `status` must be updated only through `PATCH /claims/{id}/status`.
- `totalAmount`, `damages`, `createdAt`, and `updatedAt` are not accepted from client input.

### Claim Status Update

- `status` is required.
- `status` must be one of `PENDING`, `IN_REVIEW`, `FINISHED`, or `CANCELED`.
- The requested transition must be allowed by the state transition rules.
- The high-severity finish policy must pass when transitioning to `FINISHED`.

### Damage Create

- `part` is required and must be a non-empty string.
- `severity` is required and must be `LOW`, `MID`, or `HIGH`.
- `imageUrl` is required and must be a non-empty string.
- `price` is required, numeric, and greater than 0.
- `score` is required and must be an integer from 1 to 10.
- Damage creation is allowed only when the parent claim is `PENDING`.

### Damage Update

- `part` is optional, but if provided it must be a non-empty string.
- `severity` is optional, but if provided it must be `LOW`, `MID`, or `HIGH`.
- `imageUrl` is optional, but if provided it must be a non-empty string.
- `price` is optional, but if provided it must be numeric and greater than 0.
- `score` is optional, but if provided it must be an integer from 1 to 10.
- Damage update is allowed only when the parent claim is `PENDING`.

## Error Behavior and Status Code Mapping

All API errors should return a consistent JSON shape.

Example:

```json
{
  "statusCode": 400,
  "error": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "details": [
    {
      "field": "price",
      "message": "price must be greater than 0"
    }
  ]
}
```

Status code mapping:

| Status | Error | Use |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Request body, path, or query validation failed |
| `404` | `NOT_FOUND` | Claim or damage was not found |
| `409` | `INVALID_STATE_TRANSITION` | Requested claim status transition is not allowed |
| `409` | `DAMAGE_MANAGEMENT_NOT_ALLOWED` | Damage create, update, or delete was attempted while claim is not `PENDING` |
| `422` | `BUSINESS_RULE_VIOLATION` | High-severity finish policy failed |
| `500` | `INTERNAL_ERROR` | Unexpected server error |

## API Summary

The OpenAPI contract is defined in `docs/openapi.yaml`.

Required endpoints:

- `POST /claims`.
- `GET /claims`.
- `GET /claims/{id}`.
- `PATCH /claims/{id}`.
- `PATCH /claims/{id}/status`.
- `POST /claims/{claimId}/damages`.
- `PATCH /claims/{claimId}/damages/{damageId}`.
- `DELETE /claims/{claimId}/damages/{damageId}`.

Optional query behavior:

- `GET /claims?status=PENDING` filters claims by status.

## Acceptance Criteria Mapping

| Challenge Requirement | Acceptance Criteria |
|---|---|
| Claim managers can manage claims with multiple damages | API supports claim creation, listing, detail, and damage create/update/delete under a claim |
| Claim List view | Frontend will provide a claim list backed by `GET /claims` |
| Claim Detail view | Frontend will provide a detail page backed by `GET /claims/{id}` |
| Damage table in claim detail | Claim detail response includes `damages` for table rendering |
| Add damages from claim detail | API supports `POST /claims/{claimId}/damages` and frontend will expose it in detail view |
| Damage form validation | Damage create requires `part`, `severity`, `imageUrl`, `price`, and `score` |
| Frontend total reactivity | Frontend will derive displayed total from current damages and reconcile with backend responses |
| Server total consistency | Backend calculates `totalAmount` and integration tests verify it equals the sum of damage prices |
| Damages only managed while Pending | Damage create/update/delete reject non-`PENDING` claims |
| High-severity finish rule | `IN_REVIEW -> FINISHED` rejects high-severity claims unless description length is greater than 100 |
| Dependency Injection in backend | Backend implementation will use NestJS providers, controllers, and services |
| Dependency Injection in frontend | Angular implementation will use Angular DI for API/state services |
| Business design pattern | Claim status transitions use State Machine pattern in business logic |
| MongoDB persistence | Backend implementation will persist claims and damages in MongoDB |
| Backend unit coverage greater than 95% | Unit test command will report coverage greater than 95% for backend business logic |
| Integration tests for total amount | Integration tests will create/update/delete damages and assert returned and persisted totals |
| SDD and OpenAPI-first | `docs/SPEC.md` and `docs/openapi.yaml` are created before implementation |
| AI methodology | `AI_LOG.md` will document AI usage, generated tests, corrections, and frontend reactive logic supervision |
| README with setup and coverage command | `README.md` skeleton is provided now and will be completed during implementation |
